= Nomi Processors
:idprefix:
:idseparator: -
:source-highlighter: highlight.js

Technical reference for the KSP processors behind Nomi: what they generate, the rules they
enforce, and how the modules fit together. Written for anyone working on the processors
themselves, not for consumers of the library — see link:../README.adoc[the root README] for that;
this document assumes it and covers none of it again.

== Modules

Four Gradle modules implement the KSP processors:

----
nomi-processor-common   analysis & validation only - not a runnable processor
    ↑
    ├── nomi-processor-shared   generates Nomi<Chain> resource impls + factory functions
    ├── nomi-processor-client   generates a private client impl + public ServiceCaller extension per @ClientEndpointServiceFactory
    └── nomi-processor-server   generates fun Route.<routeName>(service: <Impl>) per @ServerEndpointService
----

`nomi-processor-common` holds every verification rule from <<verifications,Verifications>> below
that a processor needs — `@Endpoint.Resource` and `Stringer` declarations (General, Resource
declarations, Path parameter types, Resource paths, Stringers, and the resource/factory half of
Generated-name collisions), plus everything about `@Endpoint.Service` interfaces and the endpoint
functions they declare (Service declarations, Endpoint functions, Endpoint parameters, Endpoint
return types) — added once `nomi-processor-server` needed them, and reused as-is by
`nomi-processor-client`, since both read the identical service-side rules via the same
`ServiceAnalyzer`. Per that section: _"each processor verifies every declaration it reads,
including ones from a dependency module — it never assumes a dependency was already checked by
whichever processor built it."_ Only ``@ServerEndpointService``'s own rules (Server
implementations, below) live in `nomi-processor-server`, and only
``@ClientEndpointServiceFactory``'s own rules (Client factories, below) live in
`nomi-processor-client` — each module validates just the one annotation it actually reads.

== The reusable surface

* `ResourceAnalyzer` (`resource/ResourceAnalyzer.kt`) is the facade a processor calls:
  `analyze(declaration)` returns a validated `AnalyzedResource`, or `null` having already reported
  every violation — never a partially-built result. `analyzeAll` does the same for a batch.
* `Reporter` (`Reporter.kt`) is the seam that keeps every check testable without a live KSP
  round: checks report through `Reporter.error(at, message)` rather than calling `KSPLogger`
  directly. `LoggingReporter` adapts it to a real `KSPLogger`; `RecordingReporter` is the test double.
* `resourcePath(simpleName, declaredPath, ownParameters)` (`path/ResourcePathParser.kt`) is a
  _pure_ function — no KSP import at all — that derives or parses a resource's path per
  <<resource-paths,Resource paths>> below. Being pure, it's tested directly with `kotlin-test`, no
  compiler needed.
* `StringerResolver.resolveFor(owner, ownerName, type, stringed, scopes, user)`
  (`stringer/StringerResolver.kt`) resolves a `Stringer` for any already-nullability-stripped
  `KSType`, given a nearest-first list of annotation scopes from `scopesOf(chain)`. It serves both a
  resource path parameter and an endpoint query parameter — the nullability-stripping and "is this
  the request body?" decisions are the _caller's_ job, kept out of this function on purpose; `owner`
  is only the diagnostic's location (a `KSPropertyDeclaration` and a `KSValueParameter` share this
  one path but aren't both `KSDeclaration`s), so the caller passes `ownerName` itself.
* `ServiceAnalyzer` (`service/ServiceAnalyzer.kt`) is the `@Endpoint.Service` analogue of
  `ResourceAnalyzer`: `analyze(declaration)` collects a service's own endpoints plus those of every
  `@Endpoint.Service` interface it extends (breadth-first, each interface visited once), validating
  each endpoint's function shape (`EndpointChecks`), body/query parameters (`EndpointParamChecks`)
  and `Either<V, E>` return type (`ReturnTypeChecks`) along the way — returning `null`, having
  already reported every violation, for an invalid service. An endpoint's Stringer scope starts at
  the interface that _declares_ it, not the leaf service being analyzed (see <<stringers,Stringers>>
  below).
* `StrayAnnotationChecks` (`general/StrayAnnotationChecks.kt`) implements <<general,General>>'s
  "Stray annotations are errors" — a purely _positional_ sweep, called once per round by all three
  processors, over every symbol carrying `@Endpoint`, `@Endpoint.Query`, `@Endpoint.Stringed` or
  `@Endpoint.UseStringer` (the four Nomi annotations that decorate something _else_, rather than
  being the sole trigger of some processor's own `getSymbolsWithAnnotation` call). It checks only
  whether the annotated symbol's immediately enclosing declaration carries the right _kind_ of Nomi
  annotation — never that declaration's own shape, which stays `ResourceChecks`/`ServiceChecks`'s job.
* `NomiFq` (`NomiFqNames.kt`) is the one place every Nomi annotation's fully-qualified name is
  written down as a string constant.

Each check function carries a one-line `// SPECS.adoc § <section>` comment naming the rule it
implements, rather than restating the rule in prose — the rule itself lives in exactly one place
(this document), so a spec change is a `grep` away from every place that implements it.

[#verifications]
== Verifications

Before generating any code, the processors verify that the `@Endpoint.*` annotations (and the declarations they
decorate) are used correctly. All rules below live in `nomi-processor-common`, so the three processors report
identical diagnostics; each processor verifies every declaration it reads, including ones from a dependency module —
it never assumes a dependency was already checked by whichever processor built it.

A violation is reported with `KSPLogger.error(message, symbol)` on the offending declaration or annotation argument.
A processor collects every violation in a round rather than stopping at the first, and generates nothing for that
round if any declaration it would need is invalid — never a partial file. A type that KSP cannot yet resolve (an
"error type") is deferred to the next round, and only reported as invalid if it is still unresolved when processing
finishes.

The rules below state the error condition, not the happy path; a bullet marked _(relaxable)_ is a candidate for
loosening later, called out because it forbids something merely unneeded by the current examples, not something
unsound.

=== General

* A declaration Nomi reads must be `public` or `internal`; `private`, `protected`, local and anonymous declarations
  are errors.
* A generated declaration is exactly as visible as the declaration it derives from; a declaration must not reference,
  anywhere the generated code reproduces it, a declaration less visible than itself (a public service must not use an
  internal resource, `Stringer`, parameter type or return type, and so on).
* No declaration Nomi reads may be `expect`/`actual`, `external`, `inner`, or local.
* No declaration Nomi reads may declare type parameters: resources, services, endpoint functions, server
  implementations and client factory objects are all required to be fully concrete.
* A `typealias` is resolved to its expansion and verified as that expansion.
* Every argument to a Nomi annotation must be a compile-time constant KSP can read.
* *Stray annotations are errors.* A processor collects every symbol carrying a Nomi annotation and
  rejects any it does not consume in that position: `@Endpoint` on a function that is not a service
  endpoint; `@Endpoint.Query` on a parameter of a non-endpoint function; `@Endpoint.Stringed` on
  anything other than a resource path parameter, an endpoint query parameter or a multipart part payload;
  `@Endpoint.UseStringer` on anything other than a resource, a service, an endpoint function, a part type
  or an annotation class.
* A use-site target that moves a Nomi annotation off the declaration being read (`@get:Endpoint.Stringed`,
  `@field:Endpoint.Stringed`, …) is an error — reachable only for `@Endpoint.Stringed` on a resource
  property; a plain function parameter (an endpoint's body or query parameter) has no alternate
  use-site target to redirect an annotation to.

=== Resource declarations (`@Endpoint.Resource`)

* Must be an `interface`. A class, object, annotation class, enum class, value class or `fun interface` is an error.
* Placement: a *root* resource is top-level, or nested only inside plain declarations (non-local, at least as
  visible as itself, and not themselves `@Endpoint.Resource`); a *nested* resource is declared directly inside the
  resource interface it extends.
* A nested resource's immediately enclosing resource interface must be its supertype directly — not reached
  indirectly through another interface, and not skipping a nesting level.
* A resource interface has no supertype other than that one; a root resource has none at all.
* A resource interface must not extend `EndpointService`, and must not also be annotated `@Endpoint.Service`.
* Every interface nested directly inside a resource interface must itself be annotated `@Endpoint.Resource`.
* No other nested declaration is allowed: no class, object, `companion object`, enum class, annotation class or
  typealias.
* No functions at all, including `suspend` ones, ones with a default body, `operator` functions, and explicit
  `toString`/`equals`/`hashCode` overrides — the shared processor's generated `data class`/`data object` supplies
  those.
* Only `val` properties are allowed; `var` is an error.
* Every property must be abstract: no initializer, no getter body, no delegate (`by`), and not `const` or `lateinit`.
* No extension properties, no property type parameters, and no `@JvmStatic`/`@JvmField`/`@JvmName` on a property.
* No property may `override` anything.
* A property name must not shadow one already declared by any ancestor in the resource's chain: they all become
  parameters of one generated class, and names in one ktor route.
* A property name must match `[A-Za-z_][A-Za-z0-9_]*` — no backticked identifiers, no `$`, no non-ASCII characters.

=== Path parameter types

* A resource property's type must be non-nullable.
* Must not be a type parameter, a star projection, a functional type, an array, `Unit`, `Nothing` or `Any`.
* Must have a `Stringer` that resolves per the Stringers rules below.
* A parameterized type (`List<Int>`, say) can only be given a `Stringer` through `@Endpoint.Stringed` on the specific
  property, since `@Endpoint.UseStringer(type = …)` can only name a raw class, not a parameterized one.

[#resource-paths]
=== Resource paths

* An empty `path` is derived: the interface's simple name with a lowercase first letter, followed by one segment per
  own path parameter, in declaration order.
* When derived this way, the simple name must already be usable as a path segment as-is
  (`[A-Za-z][A-Za-z0-9_-]*`); an interface whose name does not fit must be given an explicit `path`.
* A non-empty `path` must not be blank, must not start or end with `/`, and must contain no empty segment (`//`).
* A `path` must contain none of `?`, `#`, `&`, `=`, whitespace, or a scheme/authority — it names path segments only.
* A `path` must contain no `%`: literal text is percent-encoded by the runtime on its way out, so a pre-encoded path
  would be encoded a second time.
* A `{}` placeholder must be balanced, must not be nested, and must name something non-empty.
* ktor's `*` wildcard, `{...}` tailcard, `{name...}` and `{name?}` syntaxes are all errors — Nomi routes are static.
* At most one placeholder per path segment, with an optional literal prefix and/or suffix in that same segment
  (`p:{postId}`, `{id}.json` are both fine); `{a}-{b}` in one segment is an error, since ktor cannot route it.
* Each of the resource's own path parameters must appear as a placeholder exactly once in its `path`; appearing zero
  or two-or-more times is an error.
* A placeholder naming anything other than one of the resource's own path parameters is an error — in particular, one
  naming an inherited path parameter, which is already part of the parent's path and must not be repeated.
* Every resource contributes at least one path segment; a resource whose derivation would produce zero segments
  cannot be expressed. _(relaxable)_

NOTE: Two distinct resource interfaces are allowed to resolve to the same full path. Only two _endpoints_ resolving
to the same `(path, method)` pair is an error (see Service declarations below) — a bare path collision with no
method conflict is legal.

[#stringers]
=== Stringers

* The `with` argument (in `@Endpoint.Stringed` and `@Endpoint.UseStringer`) must name an `object` declaration —
  a named object or a `companion object` are both fine; a class, interface, abstract class, enum class, anonymous
  object or local object is an error.
* Must be non-local, and `public` or `internal`, at least as visible as every declaration that uses it.
* Must implement `Stringer<T>` for a concrete `T`; implementing raw `Stringer<*>`, or `Stringer<TypeParam>` through
  its own type parameter, is an error.
* `T` must be exactly the property's or parameter's type, nullability stripped for an optional query parameter —
  `Stringer<Number>` used for an `Int` property is an error, since `decode` must produce the declared type exactly.
* `@Endpoint.Stringed` on the request-body parameter of an endpoint is an error (the body has no `Stringer`; it is
  (de)serialized as a whole — see the root README's Wire protocol section).
* `type` must name a class with no type parameters, and must not be `Unit`, `Nothing`, `Any`, an array, an annotation
  class or a functional type. Enum classes, value classes and ordinary classes are all fine.
* Two registrations for the same `type` reaching one declaration at the same scope distance and the same
  annotation depth are an ambiguity error only when they name a different `with`; naming the same `with` twice this
  way is a harmless duplicate and is accepted.
* Every annotation in a walked carrier-annotation chain must have `BINARY` or `RUNTIME` retention — a `SOURCE`
  annotation is absent from the class file, so it would resolve within its own module and silently fail to resolve
  from a dependent one. (A carrier meant to be applied to another annotation must also declare
  `AnnotationTarget.ANNOTATION_CLASS`, but Kotlin itself already rejects a misapplied annotation at its use site, so
  Nomi does not re-check applicability.)
* A scope is any declaration that may carry `@Endpoint.UseStringer`: an endpoint function, a resource or service
  interface, a `@Endpoint.MultipartFormData` part type, or a carrier annotation class. A query parameter's scope chain
  is its endpoint function, then the interface that declares it and each interface outward; a part payload's is the
  endpoint function, then the part type, then that same interface chain; a path parameter's is the resource chain
  alone — an endpoint's registration never reaches it, since a resource is analysed once and its generated factory
  has one encoding.
* `@Endpoint.UseStringer` is collected by walking the full annotation tree reachable from each scope: its own
  annotations, the annotations on those annotation classes, and so on to any depth. The walk is
  breadth-first and visits each annotation class at most once, so it terminates on a cyclic annotation reference and
  collapses a diamond into a single visit; each registration is recorded at the shallowest depth it is found at.
* When no `Stringer` resolves for a type that needs one, the reported error names the type and the property or
  parameter that needed it.

[#service-declarations-endpointservice]
=== Service declarations (`@Endpoint.Service`)

* Must be an `interface`; not `sealed`, not `fun interface`.
* Must be top-level, or nested only inside plain declarations — never inside a resource interface.
* Must extend `EndpointService`, directly or transitively.
* Every other supertype must itself be `@Endpoint.Service`, or a plain interface declaring no members at all; an
  unannotated supertype that declares members (in particular, endpoint-shaped methods) is an error.
* Endpoints are collected from the whole `@Endpoint.Service` hierarchy: the interface's own methods, plus those of
  every `@Endpoint.Service` interface it extends, transitively.
* A service must not `override` an endpoint it inherits — doing so would register the same route twice.
* The only members allowed on a service interface are endpoint functions: no properties, no nested types, no
  `companion object`, no typealias.
* No two endpoints of one service — own or inherited — may resolve to the same `(path, method)` pair.
* A service declaring zero endpoints is legal (for instance, a base interface that exists only to carry
  `@Endpoint.UseStringer` for the interfaces that extend it).
* A service interface must not also be annotated `@Endpoint.Resource`.

=== Endpoint functions

* Must be `suspend`.
* Must be abstract; a default body on an endpoint method is an error.
* Must have an extension receiver, and that receiver must be a non-nullable `@Endpoint.Resource` interface type with
  no type arguments.
* Must declare no type parameters, and must not be `inline`, `infix`, `operator`, `external` or `tailrec`; no
  `@JvmName`/`@JvmStatic`.
* Its HTTP method comes from `@Endpoint(method)` when present — the annotation always wins, even over a name that
  looks like a different verb. Without `@Endpoint`, the function's name must be exactly one of `get`, `post`, `put`,
  `patch` or `delete`, lowercase; any other name without `@Endpoint` is an error.
* The function name must be a plain identifier — no backticked name. _(relaxable)_
* The receiver resource's generated implementation must be available: either the resource is declared in the module
  under compilation, or its `Nomi…` implementation resolves from a dependency whose shared processor already ran.
  Otherwise, the error names the resource whose generated implementation is missing.

=== Endpoint parameters

* Every parameter is either the request body (must be first, and unannotated) or a query parameter (annotated
  `@Endpoint.Query`). An unannotated parameter anywhere but first is an error.
* A body parameter is allowed only when the HTTP method is `Post`, `Put` or `Patch`; one on `Get` or `Delete` is an
  error.
* The body parameter must not be `vararg`, must have no default value (the server always reads it from the request,
  so a default could never apply), and must be non-nullable.
* The body parameter's type must not be `Unit`, `Nothing`, a functional type or a type parameter.
* The body parameter must carry neither `@Endpoint.Stringed` nor `@Endpoint.Query`.
* A query parameter must not be `vararg`.
* A *non-nullable* (required) query parameter must not have a default value: the server answers `400 Bad Request`
  when it is absent, so a default could never be reached.
* A *nullable* (optional) query parameter may have any default value, including a non-`null` one — defaults apply
  only at the call site, on the client; the server always passes either the decoded value or `null` explicitly. This
  is documented behavior, not an error.
* A query parameter's type must have a `Stringer` that resolves (nullability stripped for the purpose of resolution);
  it must not be `Unit`, `Nothing`, `Any`, a functional type, a type parameter or an array.
* The effective query parameter name — ``@Endpoint.Query(name)``'s argument, or the parameter's own name when that
  argument is empty — must be non-blank and match `[A-Za-z_][A-Za-z0-9_.-]*` (no `&`, `=`, `?`, `#`, `%`, `+`, or
  whitespace).
* Two query parameters of the same endpoint must not resolve to the same effective name.
* A query parameter's effective name must not collide with the name of any path parameter along the receiver's
  resource chain: ktor's `RoutingCall.parameters` merges path and query parameters, so such a collision would make
  the value read at that name ambiguous.
* Every endpoint parameter name must be a plain identifier, since it is reproduced as a named argument in generated
  code.
* A parameter typed `EndpointService.Multipart<T>` is the request body in `multipart/form-data` form, and obeys every
  body rule above: it must be first and unannotated, is allowed only on `Post`, `Put` or `Patch`, and must not be
  `vararg`, have a default value, be nullable, or carry `@Endpoint.Query` or `@Endpoint.Stringed`.
* An endpoint declares either an ordinary body or a `Multipart<T>` parameter, never both.
* `T` must be a part type — an interface annotated `@Endpoint.MultipartFormData`, see
  <<multipart-part-types,Multipart part types>>. A star projection, a type parameter, or a type without that
  annotation is an error.

=== Endpoint return types

* Must resolve to `org.kodein.rest.nomi.Either<V, E>` — written directly, or through a `typealias` that expands to
  it (per the general typealias rule above), including a parameterized one such as `typealias Ok<V> = Either<V,
  NoFail>` used as `Ok<UserDetails>`.
* Every rule below applies to the expansion: it must not be a supertype of `Either`, must not be nullable (a
  `typealias` onto a nullable `Either` is still an error), must carry no star projection, and both type arguments
  must be concrete after expansion — never a type parameter.
* `E` must be a concrete, non-nullable type implementing `Error`; `Error` itself, and `Nothing`, are both errors.
* `V` must not be `Nothing`, `Any`, `Any?` or `Unit?`.
* *`V` and `E` must be disjoint*: neither may be a subtype of the other, and they must not be the same type.
  `Either` stores one value and discriminates between success and failure with `isInstance` (see `Either.kt`); any
  overlap between `V` and `E` would make a failure indistinguishable from a value at runtime.
* `V` may be `Unit`, or nullable — both cases answer `204 No Content` (see the root README's Wire protocol section).
* `NoFail` must not be used as `V`.

[#multipart-part-types]
=== Multipart part types (`@Endpoint.MultipartFormData`)

A part type names the parts a `multipart/form-data` body may carry, one part per direct subtype, and is what a
`Multipart<T>` endpoint parameter is parameterized by. The subtype is the part; its single property is the part's
payload.

* Must be a `sealed interface`; a class, an abstract class, an enum, an object or a non-sealed interface is an error.
* Must declare at least one part.
* Every part must be a *direct subtype nested inside the part type itself*.
* Every part must be a `data class` with exactly one `val` primary-constructor property, declaring no further
  property and no type parameter. An `object`, a further `sealed` level, or a subtype with zero or several
  properties is an error.
* A part's payload type is that property's type. `EndpointFile` makes it a *file part*; any other type makes it a
  *value part*, and must have a `Stringer` that resolves — the same resolution as a query parameter's, with the
  nearest-wins scope starting at the endpoint function, then the part type, then the service that declares the
  endpoint.
* The effective part name — ``@Endpoint.MultipartFormData.Part(name)``'s argument, or the subtype's simple name with
  a lowercase first letter when that argument is empty — must be non-blank and match the same
  `[A-Za-z_][A-Za-z0-9_.-]*` pattern a query parameter name must.
* Two parts of the same part type must not resolve to the same effective name.
* ``@Endpoint.MultipartFormData.Part``'s `presence` fixes the part's cardinality, defaulting to
  `PartPresence.Required`. It drives both the generated builder's parameter shape and what the server enforces:

[cols="1,1,2,2"]
|===
| `PartPresence` | Cardinality | Builder parameter | Server

| `Required`
| Exactly one
| `p: T`
| `400` when absent, and on a second occurrence

| `Optional`
| Zero or one
| `p: T? = null`
| `400` on a second occurrence

| `RepeatedRequired`
| One or more
| `p: List<T>`
| `400` when absent

| `RepeatedOptional`
| Zero or more
| `p: List<T> = emptyList()`
| never rejected on cardinality
|===

A part name the peer sends that the endpoint does not declare is a `400`, raised by the generated `when`'s `else`
branch — a part type is a closed set, not a prefix of one.

[#server-implementations-serverendpointservice]
=== Server implementations (`@ServerEndpointService`)

* Must be a concrete `class` or `object`; an interface, abstract class, sealed class, annotation class or enum class
  is an error.
* Must not be `inner`, local or anonymous; must be `public` or `internal`; must be top-level or nested only inside
  plain declarations.
* Must implement at least one `@Endpoint.Service` interface, directly or transitively.
* Across _all_ the services it implements together, no two endpoints may resolve to the same `(path, method)` pair —
  they would all be registered on the one `Route` this class's generated function builds.
* Every endpoint it must implement needs its receiver resource's implementation resolvable (see Endpoint functions
  above) and every `Stringer` it needs resolvable (see Stringers above).
* `routeName` must be non-blank, match `[A-Za-z_][A-Za-z0-9_]*`, and must not be a Kotlin hard keyword.

[#client-factories-clientendpointservicefactory]
=== Client factories (`@ClientEndpointServiceFactory`)

* Must annotate an `object` declaration; a class, interface, annotation class or enum class is an error.
* Must not be a `companion object`, a local object or an anonymous object _(relaxable)_; must be `public` or
  `internal`; must be top-level or nested only inside plain declarations.
* `serviceClass` must name an interface annotated `@Endpoint.Service` — the type system alone only guarantees it
  extends `EndpointService`.
* `name` must be non-blank, match `[A-Za-z_][A-Za-z0-9_]*`, and must not be a Kotlin hard keyword.
* On one annotated object, `serviceClass` must not repeat, and no two of its `@ClientEndpointServiceFactory`
  annotations may share a `name`.
* The generated `<Object>.<name>` extension function must not collide with an existing member or extension of that
  object, nor with another generated extension of it.
* Every endpoint of the named service must itself be generatable: its receiver resource's implementation must
  resolve, and every `Stringer` it needs must resolve.

=== Generated-name collisions

* A resource's generated implementation is named `Nomi`, followed by the simple names of the resource interface and
  of every interface or plain declaration it is nested in, outermost first. Two resources in the same package must
  not produce the same generated name this way (for example a top-level `Users` with a nested `New`, next to an
  unrelated top-level `UsersNew`) — the error names both.
* A resource's generated factory function is top-level for a root resource, or an extension of the parent resource
  for a nested one. No two generated factory functions may collide on (receiver, name).
* A client implementation, named `Nomi<Object><Service>Client`, must be unique per package.
* A part type's generated builder is an extension on the `@ClientEndpointServiceFactory` object, named `multipart`
  followed by the simple names of the part type and of every declaration it is nested in, outermost first. Two part
  types reached from the same factory object must not produce the same builder name this way, and a builder must not
  collide with a resolvable user declaration on that object.
* Generated file names must be unique per package.
* A generated declaration must not collide with a resolvable user declaration in the same package.

[#deliberately-not-verified]
=== Deliberately not verified

* *Serializability* of `V`, `E`, or a request body type. Serialization is outside Nomi's scope (see the root
  README's Wire protocol section); a type missing `@Serializable` (or a sealed hierarchy member missing it)
  surfaces from the serialization plugin itself, or as a runtime failure — not from a Nomi processor.
* Client and server *configuration* (`ContentNegotiation`, the base URL, the `Content-Type`) is invisible to a
  processor and is reported at runtime instead (see the root README for client/server configuration).
* Whether a `Stringer` round-trips (`decode(encode(v)) == v`), or wrongly escapes its own output.
* Whether a blanket `@Endpoint.UseStringer` registration is ever actually used by anything in scope.
* An `(path, method)` collision between two services that are never implemented together by the same
  `@ServerEndpointService` class, or between two such classes mounted on the same ktor `Route` at runtime — neither
  is visible to a processor.
* Two distinct resources resolving to the same path (explicitly allowed — see Resource paths above).

== Code generation

=== Shared processor

For each `@Endpoint.Resource` interface, the shared processor generates a public implementation of that interface,
annotated with `@InternalNomiAPI`, whose name is the concatenation of the simple names of the interface and of all of
its enclosing resource interfaces, prefixed with `Nomi`.
It is a `data object` when the resource has no path parameter at all, and a `data class` otherwise, holding its own
path parameters as well as every path parameter it inherits from its parents.

It also generates an associated factory function that allows the user to create the data object or class by emulating
the nested resource route: a top-level function for a root resource, an extension function on the parent resource for
a nested one. That function takes only the resource's own path parameters — the inherited ones are read from the
receiver.

Example:

[source,kotlin]
----
@InternalNomiAPI public data object NomiUsers : Users
@InternalNomiAPI public data object NomiUsersNew : Users.New
@InternalNomiAPI public data class NomiUsersUser(override val userId: Uuid) : Users.User
@InternalNomiAPI public data class NomiUsersUserPosts(override val userId: Uuid) : Users.User.Posts
@InternalNomiAPI public data class NomiUsersUserPostsPost(
    override val userId: Uuid,
    override val postId: Uuid,
) : Users.User.Posts.Post

@OptIn(InternalNomiAPI::class)
context(_: EndpointService)
public fun Users(): Users = NomiUsers

@OptIn(InternalNomiAPI::class)
context(_: EndpointService)
public fun Users.New(): Users.New = NomiUsersNew

@OptIn(InternalNomiAPI::class)
context(_: EndpointService)
public fun Users.User(userId: Uuid): Users.User = NomiUsersUser(userId)

@OptIn(InternalNomiAPI::class)
context(_: EndpointService)
public fun Users.User.Posts(): Users.User.Posts = NomiUsersUserPosts(userId)

@OptIn(InternalNomiAPI::class)
context(_: EndpointService)
public fun Users.User.Posts.Post(postId: Uuid): Users.User.Posts.Post = NomiUsersUserPostsPost(userId, postId)
----

The `context(_: EndpointService)` context parameter ensures that a resource can only be built inside a service call.

A `@Endpoint.MultipartFormData` part type needs nothing from this processor: its parts are written by the user, and
its builder is emitted by the client processor, which is the only side that may name `ListMultipart`.

=== Server processor

For each `@ServerEndpointService` annotated class, the server processor generates, in the same package, a `fun Route.<routeName>(service: <ServiceImplementation>)` function, named after the annotation's `routeName` argument.
That function registers all endpoints declared in all `@Endpoint.Service` interfaces this class implements.

For each endpoint, the function generates a nested ktor route and calls the associated service method with:

* The resource object implementation generated by the shared processor.
* An input parameter received from ktor (if it has an input)
* Every query parameter the endpoint declares.

All of the HTTP method handlers of a given path are siblings inside that path's `route { }` block: a handler block
(`get { }`, `delete { }`, …) must never contain another handler declaration, as that would register the inner route
lazily — and repeatedly — while serving the outer one.

Example:

[source,kotlin]
----
@OptIn(InternalNomiAPI::class)
fun Route.users(service: ServerUsersService) {
    route("/u") {
        get {
            call.respond(service) {
                NomiUsers
                    .get(
                        page = decodeOrNull(IntStringer, call.queryParameters["page"])
                    )
            }
        }
        route("/new") {
            post {
                call.respond(service) {
                    NomiUsersNew
                        .create(
                            user = call.receive()
                        )
                }
            }
        }
        route("/user/{userId}") {
            get {
                call.respond(service) {
                    NomiUsersUser(
                        userId = decode(UuidStringer, call.parameters["userId"]!!)
                    )
                        .get()
                }
            }
            delete {
                call.respond(service) {
                    NomiUsersUser(
                        userId = decode(UuidStringer, call.parameters["userId"]!!)
                    )
                        .delete()
                }
            }
          // ...
        }
    }
}
----

Note that `decode`, `decodeOrNull`, `decodeRequired` and `call.respond` are public functions provided by the runtime,
under the `@InternalNomiAPI` optin annotation:

* `decode(stringer, value: String)` decodes a path parameter, and raises `400 Bad Request` when the `Stringer` fails.
* `decodeOrNull(stringer, value: String?)` decodes an optional query parameter, and returns `null` when it is absent.
* `decodeRequired(stringer, name, value: String?)` decodes a required query parameter, and raises `400 Bad Request`
  when it is absent.

An endpoint taking a `Multipart<T>` reads `call.receiveMultipart()` instead of `call.receive()`, and wraps it in an
`EndpointMultipartReceiver` carrying the part-presence map from the declaration and a transform that decodes one
`PartData` into a part:

[source,kotlin]
----
post {
    call.respond(service) {
        NomiTools.post(
            EndpointMultipartReceiver(
                service = this,
                multipart = call.receiveMultipart(),
                parts = mapOf(
                    "file" to Endpoint.MultipartFormData.PartPresence.Required,
                    "from" to Endpoint.MultipartFormData.PartPresence.Optional,
                    "article" to Endpoint.MultipartFormData.PartPresence.RepeatedRequired,
                ),
            ) {
                when (it.name) {
                    "file" -> ToolsPostData.File(it.asEndpointFile("file"))
                    "from" -> ToolsPostData.From(it.asEndpointValue("from", UuidStringer))
                    "article" -> ToolsPostData.With(it.asEndpointValue("article", ArticleContentJsonStringer))
                    else -> httpError(HttpStatusCode.BadRequest, "Unknown part '${it.name}'")
                }
            }
        )
    }
}
----

The transform dispatches on the *part name*, not on the subtype, and is keyed by the effective name — `"article"`
above, whose subtype is `With`. `EndpointMultipartReceiver` is what enforces cardinality, per the table in
<<multipart-part-types,Multipart part types>>; the `else` branch is what rejects a part the endpoint never declared.

Two more runtime functions, also under `@InternalNomiAPI`:

* `asEndpointFile(name)` decodes a file part into an `EndpointFile`, and raises `400 Bad Request` when the part is
  not a file or carries no filename. It is a member of `PartScope`, the transform's receiver — which is what ties the
  file's lifetime to its part — so it needs no import.
* `asEndpointValue(name, stringer)` decodes a value part through its `Stringer`, and raises `400 Bad Request` when
  the part is not a form item, when its declared `Content-Type` contradicts the ``Stringer``'s, or when decoding
  fails. A part carrying no `Content-Type` at all is accepted: RFC 7578 makes the header optional, and a browser
  omits it for an ordinary form field.

=== Client processor

For each `@ClientEndpointServiceFactory` annotated object, the client processor generates, in the same package:

* A private implementation of the service interface that also implements `NomiClientEndpointService`.
* A public extension function on the annotated object, named after the annotation's `name` argument,
  that creates a `ServiceCaller` for the service interface.

[source,kotlin]
----
@OptIn(InternalNomiAPI::class)
private class NomiAPIServicesUsersServiceClient(
    val client: HttpClient,
    override val buildRequest: HttpRequestBuilder.() -> Unit
) : UsersService, NomiClientEndpointService {
    override suspend fun Users.get(page: Int?): Either<List<UserSummary>, NoFail> =
        client.call(
            pathSegments = listOf(
                "u"
            ),
            method = Get,
        ) {
            appendParameter("page", page, IntStringer)
        }

    override suspend fun Users.New.create(user: NewUser): Either<Uuid, UserCreationFailure> =
        client.call(
            pathSegments = listOf(
                "u",
                "new",
            ),
            method = Post,
        ) {
            setBody(user)
        }

    override suspend fun Users.User.get(): Either<UserDetails, NoFail> =
        client.call(
            pathSegments = listOf(
                "u",
                "user",
                UuidStringer.encode(userId),
            ),
            method = Get,
        )

    //...
}

@OptIn(InternalNomiAPI::class)
public fun APIServices.users(client: HttpClient): ServiceCaller<UsersService> =
    NomiServiceCaller(
        client = client,
        service = ::NomiAPIServicesUsersServiceClient,
    )
----

A resource path that mixes literal text and a parameter inside a single segment (such as `p:{postId}`) is rendered as
the concatenation of that literal text and the encoded parameter, in a single path segment.

The client processor also generates a *builder* for every part type reached through a `Multipart<T>` parameter of
any service the annotated object exposes. A builder is an extension on that object — not on the part type, which is
therefore free of any `companion object` requirement — named `multipart` followed by the part type's name per
<<generated-name-collisions,Generated-name collisions>>. It takes one parameter per part, named after the *subtype's*
simple name lowercased, whose type and default come from the part's presence per the table in
<<multipart-part-types,Multipart part types>>.

Every builder of one object goes into a single generated file, `Nomi<Object>Multipart.kt`, beside
the per-service `Nomi<Object><Service>Client.kt`.

Builders are collected *per annotated object, by part type*:

* Two services registered on the *same* object that use the same part type yield **one** builder — the object is the
  unit of deduplication, not the service.
* The same part type reached from two *different* objects yields **two** builders, one on each, since each object
  owns the API surface its own users see.

An endpoint taking a `Multipart<T>` encodes it by draining it into ktor's `formData`, dispatching on the sealed
subtype:

[source,kotlin]
----
@OptIn(InternalNomiAPI::class)
public fun APIServices.multipartToolsPostData(
    file: EndpointFile,
    from: Uuid? = null,
    with: List<ArticleContent>,
): EndpointService.Multipart<ToolsPostData> =
    ListMultipart(
        buildList {
            add(ToolsPostData.File(file))
            if (from != null) {
                add(ToolsPostData.From(from))
            }
            require(with.isNotEmpty()) { "with is required" }
            addAll(with.map { ToolsPostData.With(it) })
        }
    )

override suspend fun Tools.post(parts: EndpointService.Multipart<ToolsPostData>): Either<Unit, NoFail> =
    client.call(
        pathSegments = listOf("tools"),
        method = Post,
    ) {
        setBody(
            MultiPartFormDataContent(
                formData {
                    parts.forEachPart { part ->
                        when (part) {
                            is ToolsPostData.File -> appendEndpointFile("file", part.file)
                            is ToolsPostData.From -> appendEndpointItem("from", part.from, UuidStringer)
                            is ToolsPostData.With -> appendEndpointItem("article", part.content, ArticleContentJsonStringer)
                        }
                    }
                }
            )
        )
    }
----

Note the two different keys at play: the builder's *parameter* is named after the subtype (`with`), while the part it
is encoded under is the effective *part name* (`"article"`). The `when` is exhaustive and carries no `else`.

`appendEndpointFile` and `appendEndpointItem` are runtime functions under `@InternalNomiAPI`, and `ListMultipart` is
the runtime's `Multipart<T>` over a plain list. A `Multipart<T>` is a single-pass stream in both directions: the
generated client drains the caller's one while building the body, and consuming one twice fails rather than quietly
sending nothing.

== Testing strategy

. *Pure logic*, in `nomi-processor-common`'s own `src/test`, using plain `kotlin-test-junit` —
  no KSP, no compiler, no `kctfork`. This covers anything with zero KSP dependency: path-string
  parsing (`ResourcePathParserTests`), the annotation-tree breadth-first walk
  (`AnnotationTreeWalkTests`), the nearest-wins Stringer resolution algorithm
  (`StringerResolutionTests`), and generated-name derivation (`GeneratedNameTests`).
. *Real KSP rounds*, using `dev.zacsweers.kctfork` to compile fixture source through the actual
  processor(s) and assert on `KotlinCompilation.ExitCode` and `diagnosticMessages` —
  ``nomi-processor-common``'s own `src/test` has no compiler test harness of its own, so this is
  deliberately the primary place its rules get proven correct, even though the rules themselves
  live in that other module:
+
* The `@Endpoint.Resource`/`Stringer` rule set is exercised end-to-end in
  ``nomi-processor-shared``'s `src/test`.
* The `@Endpoint.Service`/endpoint-function rule set — including
  <<multipart-part-types,Multipart part types>>, which a `Multipart<T>` endpoint parameter pulls
  in — is exercised end-to-end in ``nomi-processor-server``'s `src/test` instead, alongside that module's own
  `@ServerEndpointService` rules — the server processor was the _first_ reader of those
  declarations, so its tests double as ``ServiceAnalyzer``'s proof. ``nomi-processor-client``'s own
  tests deliberately don't re-prove this rule set — they cover only
  ``@ClientEndpointServiceFactory``'s own rules and client-specific codegen, trusting the server
  processor's tests for everything `ServiceAnalyzer` already validates identically for both. Both
  processors' `ProcessorTestSupport.compile` register _both_ `NomiSharedProcessorProvider` and their
  own provider, since a fixture's resources need their `Nomi…` implementations generated in the same
  round.

== Gotchas

* *Never use `KSAnnotated.getAnnotationsByType`/`isAnnotationPresent`.* They're `@KspExperimental`
  and reflectively load the annotation's `KClass`-typed arguments via `Class.forName` on the
  _processor's own classpath_ — which will never have the user's types (`Uuid`, a user's `Stringer`
  object, …) on it, since the processor modules deliberately carry no runtime dependency. Read
  `KSAnnotation.arguments` directly instead (see `ksp/Annotations.kt`).
* *`KSClassDeclaration.superTypes` includes `kotlin.Any`*, even for an interface with no declared
  supertype at all. Every supertype-shape check filters it first (`declaredSupertypes()`).
* *KSP/kctfork version pin*: ``kctfork:ksp:0.13.0``'s own POM requests the KSP2 implementation
  artifacts (`symbol-processing-aa-embeddable`, `-common-deps`) a version _older_ than
  `symbol-processing-api` in the version catalog. `gradle/libs.versions.toml` pins
  `ksp-aaEmbeddable` to the same version as `ksp-symbolProcessingApi` to close that gap — every
  processor module's `build.gradle.kts` carries this forward via its own `kctfork` test dependency.
* *A generated function calling an `inline` runtime function needs a matching JVM target.*
  ``nomi-runtime-server``'s `decode`/`decodeOrNull`/`decodeRequired`/`respond`, and
  ``nomi-runtime-client``'s `call`/`appendParameter`, are `inline`, compiled at this project's
  `jvmToolchain(17)`; a `kctfork` `KotlinCompilation` defaults to a lower JVM target and the Kotlin
  compiler refuses to inline JVM-17 bytecode into it. Set `jvmTarget = "17"` on the
  `KotlinCompilation` (see `nomi-processor-server`/``-client``'s `ProcessorTestSupport.kt`) wherever a
  processor's generated code calls such a function.
* *`ParameterizedTypeName`'s companion `get(ClassName, TypeName...)` overloads don't resolve from
  Kotlin source* in this project's kotlinpoet version, even though they're visible to `javap` —
  build a generic `TypeName` with the `ClassName.parameterizedBy(...)` extension instead (import
  `com.squareup.kotlinpoet.ParameterizedTypeName.Companion.parameterizedBy` — it's a _member_
  extension of the companion object, not a top-level function, so a bare
  `import com.squareup.kotlinpoet.parameterizedBy` resolves to nothing).
* *Emitting `context(_: EndpointService)`*: use KotlinPoet's `FunSpec.Builder.contextParameter(ContextParameter(type))`
  (`@ExperimentalKotlinPoetApi`, `ContextParameter(type)` defaults its name to `_`) — never the
  deprecated `contextReceivers(...)`, which emits the old receiver-style syntax and is mutually
  exclusive with context parameters at `build()`.
* *A registration's own shape is validated at _discovery_, not at _use_.* `@Endpoint.UseStringer(type = X::class, with = Y::class)`
  is checked the moment it's found while walking a resource's annotation tree, regardless of
  whether any property in scope ends up matching it — the <<deliberately-not-verified,Deliberately
  not verified>> list excuses an _unused_ registration from scrutiny, not a structurally invalid
  one. Re-validating again at resolution time would just double-report the same problem.
* *``@Endpoint.Stringed`` on a part's property binds to the constructor _parameter_, not the property.* A part is a
  `data class` whose payload is a primary-constructor `val`, and Kotlin's applicable-target priority puts `param`
  ahead of `property` — so the annotation arrives as a `KSValueParameter` whose parent is a constructor, not as a
  `KSPropertyDeclaration`. `StrayAnnotationChecks` must accept that position, or users are forced to write
  `@property:Endpoint.Stringed(…)`.
* *``asEndpointFile`` must not be imported; `asEndpointValue` must.* The first is a member extension of `PartScope`,
  the transform's receiver, and resolves inside the transform lambda with no import at all — emitting one is an
  unresolved reference. The second is top-level and needs its import like any other runtime function.
* *A part contributes `Content-Disposition` _parameters_ only.* ktor's `formData` writes
  `Content-Disposition: form-data; name="<key>"` itself and appends anything a part adds as a further value of the
  same header, which `MultiPartFormDataContent` then joins with `"; "`. A part that contributes a disposition of its
  own — even an empty one — puts a second, or a stray, `form-data` token in the middle of the header.
* *The generated `when` over a sealed part type carries no `else`*, so it is coupled to the compiler's
  exhaustiveness check rather than to a Nomi diagnostic: should a processor's view of the hierarchy ever diverge from
  the compiler's, the user sees `'when' expression must be exhaustive` inside generated source.
* *Both `formData` and `forEachPart` are `inline`.* That is the only reason the generated client can drain a
  `Multipart<T>` — a `suspend` operation — inside ``formData``'s non-suspending `FormBuilder.() -> Unit` lambda. A
  future ktor release dropping `inline` from `formData` breaks every generated client.
* *User-declaration collision checks must compare file _paths_, not file _names_.* Once KSP starts
  a second round, its own previously-generated output becomes resolvable through the same
  `Resolver` calls used to detect collisions with hand-written user code. Comparing the colliding
  symbol's `containingFile.filePath` against the current round's own _source_ file paths (not the
  generated-name string) is what tells the two apart.
