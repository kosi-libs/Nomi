= Nomi
:toc: macro
:toclevels: 2
:idprefix:
:idseparator: -
:source-highlighter: highlight.js

*Compile-time REST for Kotlin Multiplatform — declare your API once, get both sides.*

Nomi turns plain Kotlin interfaces into a working REST API. You declare _resources_ — nested
interfaces that are your routes — and _services_ — interfaces whose `suspend` functions are your
endpoints. A KSP processor generates a ktor server implementation from them; another generates a
typed ktor client. Both come from the exact same declarations, so they cannot drift apart.

.endpoints.kt
[source,kotlin]
----
@Endpoint.Resource
interface Articles {
    @Endpoint.Resource interface New : Articles
}

@Endpoint.Resource
interface Article {
    val articleId: Uuid
}

@Endpoint.Service
interface ArticlesService : EndpointService {
    suspend fun Articles.get(@Endpoint.Query page: Int? = null): Either<List<ArticleSummary>?, NoFail>
    @Endpoint(Endpoint.Method.Post)
    suspend fun Articles.New.create(content: ArticleContent): Either<Uuid, ArticleCreationFailure>
    suspend fun Article.get(): Either<ArticleContent, NoFail>
}
----

.ServerArticlesService.kt
[source,kotlin]
----
@ServerEndpointService("articles")
class ServerArticlesService : ArticlesService {
    override suspend fun Articles.get(page: Int?): Either<List<ArticleSummary>?, NoFail> = TODO()
    override suspend fun Articles.New.create(content: ArticleContent): Either<Uuid, ArticleCreationFailure> = TODO()
    override suspend fun Article.get(): Either<ArticleContent, NoFail> = TODO()
}

// Thanks to @ServerEndpointService
routing { articles(ServerArticlesService()) }
----

.main.kt
[source,kotlin]
----
@ClientEndpointServiceFactory(ArticlesService::class, "articles")
object APIServices

// Thanks to @ClientEndpointServiceFactory
val result = APIServices.articles(client).call {
    Articles().New().create(ArticleContent(title = "Foo", author = "Me", content = "Bar"))
}
----

No reflection, no runtime route table, no hand-written URLs on either side. An interface, two
generated implementations, and a compiler that rejects a client and server that disagree about the
API.

toc::[]

== Why Nomi

*One declaration, both sides.* The resource and service interfaces in `commonMain` are the only
place the API is written down. The server's routes and the client's implementation are both
generated from them, so a server and a client built against the same declaration can never
disagree about a path, a method, or a type.

*A route is a type, not a string.* Nesting `@Endpoint.Resource` interfaces _is_ the path
structure — `Article.Comments` is a route because it is declared inside `Article`. A path
parameter is a `val` on the interface that owns it, not a placeholder you match against a string
later.

*A resource can only be built inside a call.* Every generated resource factory carries
`context(_: EndpointService)`. Writing `Articles()` outside a service's `call { }` block, or
outside an endpoint implementation, does not compile — there is no such thing as a resource handle
that outlives the call it addresses.

*Business failures are in the return type.* Every endpoint returns `Either<V, E>`. The server
answers a failure with `Either.error(...)`; the client receives it back as
`CallStatus.CallFailure(error)`, typed as the very same `E`. No exception crosses the wire for a
business outcome — only for things that are actually exceptional (see
<<configuring-the-httpclient,Configuring the `HttpClient`>>).

*Everything is checked before anything is generated.* A processor validates every declaration it
reads — including ones from a dependency module — and generates nothing at all for a round in
which anything it needs is invalid. There is no partial output and no runtime "route not found".

*Serialization stays yours.* Nomi defines the _shape_ of a call — method, path, query parameters,
status code, whether a body is present — and nothing about the _format_ of that body. It hands the
value to ktor's `ContentNegotiation` and lets it serialize. JSON, CBOR, ProtoBuf, or anything else
ktor can negotiate — Nomi never picks.

*Multiplatform client, JVM server.* Resources and services live in a `commonMain` shared between
every target. The generated client runs on all of them; the generated server runs on ktor-server,
which is JVM-only.

== Setup

Nomi ships six artifacts:

[cols="2,3",options="header"]
|===
| Artifact | Purpose

| `org.kodein.rest.nomi:nomi-runtime-shared`
| `Either`, `Error`/`NoFail`, `Stringer`, and the `@Endpoint.*` annotations. A normal dependency.

| `org.kodein.rest.nomi:nomi-runtime-client`
| `ServiceCaller`, `CallStatus`, and the helpers the generated client calls. A normal dependency.

| `org.kodein.rest.nomi:nomi-runtime-server`
| `httpError`, `routingCall`, and the helpers the generated routes call (ktor-server, JVM only).

| `org.kodein.rest.nomi:nomi-processor-shared`
| Needed by any module that declares a `@Endpoint.Resource`.

| `org.kodein.rest.nomi:nomi-processor-server`
| Turns a `@ServerEndpointService` class into ktor routes.

| `org.kodein.rest.nomi:nomi-processor-client`
| Turns a `@ClientEndpointServiceFactory` object into a `ServiceCaller`.
|===

=== The shared module

Resources and services are declared in `commonMain`. Run `nomi-processor-shared` once, over the
common metadata source set, and feed its output back into `commonMain`:

.build.gradle.kts
[source,kotlin]
----
import org.jetbrains.kotlin.gradle.tasks.KotlinCompilationTask

plugins {
    kotlin("multiplatform")
    id("com.google.devtools.ksp") // Add the KSP plugin - it hosts the Nomi processors
}

kotlin {
    jvm()
    iosArm64()
    // ...your targets

    sourceSets {
        commonMain {
            // Add the KSP-generated common sources to commonMain. KSP already registers this
            // directory as an output, but IntelliJ only indexes it as source code if it is also
            // declared here explicitly.
            kotlin.srcDir(layout.buildDirectory.dir("generated/ksp/metadata/commonMain/kotlin"))
            dependencies {
                // The Nomi shared runtime: annotations, Either, Stringer. A normal dependency.
                implementation("org.kodein.rest.nomi:nomi-runtime-shared:0.1.0")
            }
        }
    }
}

dependencies {
    // Run the Nomi shared processor over the common metadata source set, once, so a single set
    // of resource implementations is generated for commonMain rather than one per target.
    add("kspCommonMainMetadata", "org.kodein.rest.nomi:nomi-processor-shared:0.1.0")
}

// Every compilation - and every per-target KSP task, which also reads commonMain as part of its
// merged source set even though it has no processor registered - consumes the KSP-generated
// commonMain sources, so all of them must wait for KSP to run.
tasks.matching { it.name != "kspCommonMainKotlinMetadata" }.configureEach {
    if (name.startsWith("ksp") || this is KotlinCompilationTask<*>) {
        dependsOn("kspCommonMainKotlinMetadata")
    }
}
----

=== Kotlin version

Every generated factory and `ServiceCaller.call` use Kotlin context parameters. This repository
builds against Kotlin 2.4.10 with no extra compiler flag, so any Kotlin version where context
parameters are available without an opt-in flag works to consume Nomi.

== Resources

=== Root and nested

A resource interface is annotated `@Endpoint.Resource`. A *root* resource is declared at the top
level (or nested only inside plain, non-resource declarations that act as a namespace); a *nested*
resource is declared directly inside the resource interface it extends, and its path is appended
to its parent's.

.Users.kt
[source,kotlin]
----
@Endpoint.Resource("u") interface Users {
    @Endpoint.Resource interface New : Users
    @Endpoint.Resource interface User : Users {
        val userId: Uuid
        @Endpoint.Resource interface Posts : User {
            @Endpoint.Resource("p:{postId}") interface Post : Posts {
                val postId: Uuid
            }
        }
    }
}
----

defines:

----
/u
/u/new
/u/user/{userId}
/u/user/{userId}/posts
/u/user/{userId}/posts/p:{postId}
----

=== Paths

Leave ``@Endpoint.Resource``'s `path` empty and it is *derived*: the interface's simple name, first
letter lowercased, followed by one segment per own path parameter, in declaration order — that's
how `User` becomes `user/{userId}` above. Give it an explicit path and it's used as written — `Post`
above gets no `post/` segment because its annotation names one explicitly, `p:{postId}`, mixing a
literal prefix with a single placeholder in one segment (`{id}.json` reads the same way, suffix
instead of prefix).

=== Path parameters

A resource's own path parameters are its abstract, non-nullable `val` properties, each needing a
`Stringer` (see <<stringers,Stringers>>). A nested resource inherits every path parameter its
parents declare — `Post` above carries both `userId` and `postId` — but its generated factory
takes only its *own*: `Users.User.Posts.Post(postId)`, reading `userId` off the receiver.

=== Building a resource

Each resource gets a function named after it, taking that resource's *own* path parameters. A root
resource's is top-level; a nested one's is an extension on its parent, so a call site reads like
the route it addresses:

[source,kotlin]
----
Articles()                     // /articles
Articles().New()               // /articles/new
Article(articleId)             // /article/{articleId}
Article(articleId).Comments()  // /article/{articleId}/comments
----

An inherited path parameter is read off the receiver, never passed again — `Comments()` takes
nothing, because `Article` already carries `articleId`.

These are callable only where an `EndpointService` is in scope: inside a `call { }` block on the
client, or inside an endpoint implementation on the server. There is nowhere else to build a
resource, which is what makes <<why-nomi,"a resource can only be built inside a call">> true.

== Services and endpoints

=== The service interface

A service is an interface annotated `@Endpoint.Service`, extending the `EndpointService` marker.
Each of its `suspend` functions, extending a resource interface, is one endpoint:

.ArticlesService.kt
[source,kotlin]
----
@Endpoint.Service
interface ArticlesService : EndpointService {
    suspend fun Articles.get(@Endpoint.Query page: Int? = null): Either<List<ArticleSummary>?, NoFail>
    @Endpoint(Endpoint.Method.Post)
    suspend fun Articles.New.create(content: ArticleContent): Either<Uuid, ArticleCreationFailure>
    suspend fun Article.get(): Either<ArticleContent, NoFail>
    suspend fun Article.delete(): Either<Unit, NoFail>
    suspend fun Article.Comments.get(@Endpoint.Query page: Int? = null): Either<List<ArticleComment>?, NoFail>
    suspend fun Article.Comments.post(comment: ArticleComment): Either<Unit, ArticleCommentFailure>
}
----

resolves to:

----
GET    /articles?page
POST   /articles/new
GET    /article/{articleId}
DELETE /article/{articleId}
GET    /article/{articleId}/comments?page
POST   /article/{articleId}/comments
----

=== The HTTP method

Name the function `get`, `post`, `put`, `patch` or `delete` and that name is the method. Annotate
it with `@Endpoint(Endpoint.Method.Post)` (or any other `Method`) and the annotation wins instead —
the function can then be named anything, as `create` is above.

=== The request body

The first parameter, when it carries no `@Endpoint.Query` — `content` in `Articles.New.create`
above. Only `post`, `put` and `patch` endpoints may declare one. That one parameter can instead be
a `Multipart<T>`, for a `multipart/form-data` body (see <<multipart-form-data,Multipart form data>>),
or an `EndpointBinary`, for a raw streamed one (see <<streaming-a-request-body,Streaming a request
body>>) — an endpoint has exactly one of the three, never two.

[#streaming-a-request-body]
=== Streaming a request body

An `EndpointBinary` body parameter means the request body *is* that binary's content, streamed —
no serialization, no `ContentNegotiation`. The client announces the binary's own content type, and
its size as `Content-Length` when it knows one:

.FilesService.kt
[source,kotlin]
----
@Endpoint.Service
interface FilesService : EndpointService {
    @Endpoint(Endpoint.Method.Put)
    suspend fun Files.put(`data`: EndpointBinary): Either<Unit, NoFail>
}
----

.main.kt
[source,kotlin]
----
APIServices.files(client).call {
    Files().put(
        EndpointBinary(
            size = 9,
            contentType = ContentType.Text.Plain,
            source = { packet },
        )
    )
}
----

Leave `size` `null` when the length is not known up front and the request goes out
`Transfer-Encoding: chunked`. Server-side the endpoint receives an `EndpointBinary` built from the
request, with `contentType` and `size` taken from its headers — `size` is `null` for a chunked
request, whose length is genuinely unknown until it ends.

NOTE: A received body is single-pass, and valid only *inside* the endpoint. Opening its `source()`
twice throws, and so does reading it after the endpoint has returned — the server has recycled the
connection by then. Read what you need while you are still in the endpoint.

``EndpointBinary`` and ``EndpointFile`` are not interchangeable, and Nomi says so rather than
letting either fail at runtime: an `EndpointFile` is one part of a multipart body and carries a file
name, so it is rejected as a whole body, and as a success type; an `EndpointBinary` is a whole body,
so it is rejected as a part payload.
An `EndpointBinary` travels either way — as a parameter it is the request body, as the success type
it is the response body (see <<streaming-a-response,Streaming a response>>).

=== Query parameters

Any other parameter, annotated `@Endpoint.Query`. A *nullable* one is optional: `null` when
absent, omitted from the URL entirely when its value is `null`, and free to carry any default —
that default applies purely at the call site. A *non-nullable* one is required: the server answers
`400 Bad Request` when it's missing. `@Endpoint.Query("p")` gives it a different name on the wire
than in code.

=== The return type

Always `Either<V, E>` (see <<eithervE,`Either<V, E>`>>) — `V` the success value (`Unit` for none),
`E` the business failure (`NoFail` for none). `V` and `E` must be different types: `Either` stores
one value and tells success from failure by checking which type it is an instance of, so an
overlap between the two would make a failure indistinguishable from a value at runtime. `V` may be
`Unit`, or nullable — the demo's `get` endpoints return a nullable list to signal "page out of
range" without a business failure — and either case answers `204 No Content`.

=== Sharing endpoints across services

A service's endpoints are the union of its own and every `@Endpoint.Service` interface it extends,
however deep. A member-less base interface is the idiomatic place to hang a project-wide
`@Endpoint.UseStringer` shared by several services (see <<stringers,Stringers>>) — it can declare
zero endpoints of its own.

[cols="2,2",options="header"]
|===
| Declaration | Route

| `suspend fun Res.get(): Either<V, NoFail>`
| `GET` on ``Res``'s own path.

| `@Endpoint(Endpoint.Method.Post) suspend fun Res.create(body: T): Either<V, E>`
| `POST`, with `body` as the request body.

| `suspend fun Res.get(@Endpoint.Query page: Int? = null): Either<V, NoFail>`
| `GET`, with `page` as an optional query parameter.

| `suspend fun Res.get(@Endpoint.Query("p") page: Int): Either<V, NoFail>`
| `GET`, with a *required* query parameter named `p` on the wire.
|===

[#eithervE]
== `Either<V, E>`

The type every endpoint returns. `E` always implements the `Error` marker interface; `NoFail` is
the built-in `Error` that means "this endpoint has no business failure" — its constructor is
private, so a value of it can never actually be produced.

NOTE: `Either` is a stopgap. Kotlin has no union types for errors yet, so there is no way to write
"this returns an `ArticleContent` *or* an ``ArticleCreationFailure``" as a type — `Either` stands in
for that union until
https://youtrack.jetbrains.com/issue/KT-68296/Union-Types-for-Errors[KT-68296: Union Types for
Errors] lands, at which point it will be replaced by a real union type and removed from the
library. Don't get too attached, and don't build your own abstractions on top of it.

[source,kotlin]
----
Either.value(articleSummaries)                    // a success
Either.error(ArticleCreationFailure.InvalidTitle)  // a business failure
Either.unit<ArticleCommentFailure>()               // shorthand for Either.value(Unit)
----

[cols="1,3",options="header"]
|===
| Function | Behaviour

| `on(value, error)`
| Folds both branches down to one result type.

| `valueOr { }`
| The value, or the block applied to the error.

| `mapValue { }`
| Transforms `V`, passing an error through unchanged.

| `mapError { }`
| Transforms `E`, passing a value through unchanged.

| `isValue()` / `isError()`
| Which branch this `Either` holds.

| `valueOrNull()` / `errorOrNull()`
| The value/error if this `Either` holds it, else `null`.

| `onValue { }` / `onError { }`
| Runs a side effect on the matching branch; returns the `Either` unchanged.

| `value()` / `error()`
| The value/error, throwing if this `Either` holds the other branch.
|===

Every function above is `inline`, reified over `V`/`E` from the call site. Each also has a plain,
non-reified overload taking an explicit `NType<V>()`/`NType<E>()`, for the rare call site where the
type can't be reified. A `when` exhausted over every other `Error` subtype can dispatch the
impossible `NoFail` case to `it.isImpossible(): Nothing`.

[#stringers]
== Stringers

Every path parameter and query parameter — and every non-file multipart part — is a `String` on
the wire. A `Stringer<T>` is the two-way conversion:

[source,kotlin]
----
public interface Stringer<T> {
    public fun encode(value: T): String
    public fun decode(encoded: String): Either<T, Stringer.Failure>
    public val contentType: ContentType get() = ContentType.Text.Plain
}
----

Escaping is not a ``Stringer``'s job — the runtime percent-encodes every path segment and query value
on its way out, and decodes it on the way back in, so `encode`/`decode` always work in *unescaped*
text. A multipart part is not percent-encoded at all: it carries its ``Stringer``'s `contentType` as
its own `Content-Type` header, which is the only place that property is used.

=== Built-ins

[cols="1,3",options="header"]
|===
| Type | Encoding

| `Boolean`
| `"1"` / `"0"`; also decodes `"true"`/`"false"`.

| `Int`
| Decimal, via `String.toIntOrNull()`.

| `Long`
| Decimal, via `String.toLongOrNull()`.

| `String`
| Passthrough — sent and received unchanged.
|===

They sit at the lowest priority of the resolution order below, so a project may register its own
`Stringer` to override one of them, exactly as for any other type.

=== Declaring one

Any other type needs a `Stringer` you write. It must be an `object`:

.Stringers.kt
[source,kotlin]
----
object UuidStringer : Stringer<Uuid> {
    override fun encode(value: Uuid): String = value.toString()
    override fun decode(encoded: String): Either<Uuid, Stringer.Failure> =
        Uuid.parseOrNull(encoded)?.let { Either.value(it) } ?: Either.error(Stringer.Failure("Invalid UUID"))
}
----

=== Registering one

Five ways, all equivalent, chosen by how widely the `Stringer` should apply —
`@Endpoint.UseStringer` is repeatable, so any of the last four can register as many types as you
need from a single place:

.On the property or query parameter itself
[source,kotlin]
----
@Endpoint.Resource interface Article {
    @Endpoint.Stringed(with = UuidStringer::class)
    val articleId: Uuid
}
----

.On one endpoint — its query parameters and multipart parts, not its receiver's path parameters
[source,kotlin]
----
@Endpoint.Service
interface ArticlesService : EndpointService {
    @Endpoint.UseStringer(Instant::class, EpochMillisStringer::class)
    suspend fun Articles.get(@Endpoint.Query since: Instant? = null): Either<List<ArticleSummary>?, NoFail>
}
----

.On the resource or service interface
[source,kotlin]
----
@Endpoint.UseStringer(type = Uuid::class, with = UuidStringer::class)
@Endpoint.Resource interface Article {
    val articleId: Uuid
}
----

.On a parent interface
[source,kotlin]
----
@Endpoint.UseStringer(type = Uuid::class, with = UuidStringer::class)
@Endpoint.Service interface ServiceBase : EndpointService
@Endpoint.Service interface ArticlesService : ServiceBase { /* ... */ }
----

.Through a carrier annotation — the recommended way to share registrations project-wide
[source,kotlin]
----
@Retention(AnnotationRetention.BINARY) // BINARY or RUNTIME - a SOURCE annotation can't resolve
@Target(AnnotationTarget.CLASS)        // from a dependent module
@Endpoint.UseStringer(Uuid::class, UuidStringer::class)        // stack one per type -
@Endpoint.UseStringer(Instant::class, InstantStringer::class)  // @Endpoint.UseStringer repeats
annotation class UseSharedStringers

@UseSharedStringers
@Endpoint.Resource interface Article {
    val articleId: Uuid
}

@UseSharedStringers
@Endpoint.Service interface ArticlesService : EndpointService {
    suspend fun Article.get(@Endpoint.Query since: Instant? = null): Either<ArticleContent, NoFail>
}
----

`InstantStringer` here is declared the same way as `UuidStringer` above — one annotation now
carries every `Stringer` a project shares between its resources and services.

=== Resolution order

The nearest declaration wins:

. `@Endpoint.Stringed` on the property, query parameter or multipart part payload itself.
. Otherwise, the endpoint function, for a query parameter or a multipart part payload.
. Otherwise, the part type, for a multipart part payload.
. Otherwise, the declaring interface and each interface outward — nearest first — checked for an
  `@Endpoint.UseStringer` reachable from its own annotation tree.
. Otherwise, the built-in `Stringer` for `Boolean`, `Int`, `Long` or `String`.

Scope distance always dominates annotation depth: a registration on a nearer scope wins over one on
a farther scope, however many carrier annotations either is reached through.

An endpoint function's registration reaches that endpoint's query parameters and multipart parts,
but never its receiver resource's path parameters — a resource is analysed on its own, and the
factory generated for it has one encoding whichever endpoint addresses it.

[#multipart-form-data]
== Multipart form data

An endpoint can take a `multipart/form-data` body instead of a negotiated one — a file upload,
typically, or a file alongside the metadata describing it. Where an ordinary body is one value,
a multipart body is a sequence of named _parts_, and Nomi asks you to declare what those parts are.

=== Declaring the parts

A _part type_ is a `sealed interface` annotated `@Endpoint.MultipartFormData`, with one nested
`data class` per part. Each part holds exactly one property: its payload.

.ToolsPostData.kt
[source,kotlin]
----
@Endpoint.MultipartFormData
sealed interface ToolsPostData {

    data class File(val file: EndpointFile) : ToolsPostData

    @Endpoint.MultipartFormData.Part(presence = PartPresence.Optional)
    data class From(val from: Uuid) : ToolsPostData

    @Endpoint.MultipartFormData.Part(name = "article", presence = PartPresence.RepeatedRequired)
    data class With(
        @Endpoint.Stringed(ArticleContentJsonStringer::class)
        val content: ArticleContent,
    ) : ToolsPostData
}
----

A payload typed `EndpointFile` makes a _file part_; any other type makes a _value part_, and needs
a `Stringer` exactly as a query parameter does (see <<stringers,Stringers>>) — resolved from the
endpoint function, then the part type, then outward through the declaring service.

A part's name on the wire is the subclass's own name with a lowercase first letter — `file`,
`from` — or ``@Endpoint.MultipartFormData.Part``'s `name` argument when you give one, as `With`
does to arrive as `article`.

Its `presence` argument fixes how many times the part may occur, and drives both ends:

[cols="1,1,1,2",options="header"]
|===
| `PartPresence` | Occurrences | Sending | Receiving

| `Required` _(default)_
| Exactly one
| `p: T`
| `400` when absent, and on a second one

| `Optional`
| Zero or one
| `p: T? = null`
| `400` on a second one

| `RepeatedRequired`
| One or more
| `p: List<T>`
| `400` when absent

| `RepeatedOptional`
| Zero or more
| `p: List<T> = emptyList()`
| never rejected on count
|===

=== The endpoint

A multipart endpoint takes one `Multipart<T>` parameter where an ordinary body would go — first,
unannotated, on a `post`, `put` or `patch`. It replaces the body rather than joining it: an
endpoint has one or the other, never both.

.MPService.kt
[source,kotlin]
----
@Endpoint.Service
interface MPService : EndpointService {
    suspend fun Tools.post(parts: Multipart<ToolsPostData>): Either<Unit, NoFail>
}
----

=== Sending one

The client processor generates a builder on your `@ClientEndpointServiceFactory` object, named
`multipart` followed by the part type's name, with one parameter per part shaped by its presence:

.main.kt
[source,kotlin]
----
APIServices.mp(client).call {
    Tools().post(
        APIServices.multipartToolsPostData(
            file = EndpointFile(fileName = "foo.txt", fileSize = 8, source = { source }),
            from = Uuid.random(),
            with = listOf(ArticleContent("Yay", "Salomon", "This is cool!")),
        )
    )
}
----

One builder is generated per object, however many of its services use that part type; two different
factory objects each get their own.

=== Receiving one

`forEachPart` is how a server reads them, and the `when` over the sealed part type is exhaustive —
add a part later and every handler stops compiling until it is dealt with:

.ServerMPService.kt
[source,kotlin]
----
override suspend fun Tools.post(parts: Multipart<ToolsPostData>): Either<Unit, NoFail> {
    var file: String? = null
    var from: Uuid? = null
    val articles = mutableListOf<ArticleContent>()

    parts.forEachPart { part ->
        when (part) {
            // Read now: the file is only valid inside this handler.
            is ToolsPostData.File -> file = part.file.source().use { it.readString() }
            is ToolsPostData.From -> from = part.from
            is ToolsPostData.With -> articles += part.content
        }
    }

    return Either.unit()
}
----

A part the peer sends that the part type never declared is a `400`, as is one that breaks its
declared `presence`.

=== Part lifetime

A multipart body is a single-pass stream, and each part is released as soon as its handler returns.

NOTE: An ``EndpointFile``'s content is only valid *inside* the handler that received it. Read what
you need while you are still in the loop — copying the bytes out, or streaming them straight to
their destination. Keeping the `EndpointFile` and reading it after `forEachPart` has moved on
throws `IllegalStateException`, because the buffer it would read from is gone.

The same one-pass rule holds on the client: a `Multipart<T>` you build is consumed as the request
body is written, so build a fresh one per call rather than reusing one.

== Wire protocol

[cols="1,3",options="header"]
|===
| Status | When

| `200 OK`
| A successful call; the body is the serialized `V`.

| `204 No Content`
| A successful call with nothing to return — `V` is `Unit`, or `V` is nullable and its value is
  `null`. No body.

| `422 Unprocessable Entity`
| A business failure; the body is the serialized `E`. Reserved by Nomi: `httpError` refuses this
  code, and the client reads any *other* non-success status as an HTTP-level error rather than a
  business failure.

| `400 Bad Request`
| A path or query parameter's `Stringer` failed to decode it, or a required query parameter was
  missing. The body is the `Stringer.Failure` reason. A multipart body adds its own causes: a
  missing required part, a second occurrence of a part that may not repeat, a part the endpoint
  never declared, a part of the wrong kind, and a part whose `Content-Type` contradicts its
  ``Stringer``'s. A streamed body adds one more: a malformed `Content-Type` header.

| _(anything else)_
| Whatever `httpError(code, message)` raised, with `message` as the body when one was given.
|===

Serialization itself is entirely yours to configure — Nomi never reads or writes a negotiated body.
Register ktor's `ContentNegotiation` with the same format on both the server and the client
(`json(SharedJson)` throughout this README, because the demo uses JSON; CBOR or anything else ktor
supports works identically).

A `multipart/form-data` body is the one exception, and only partly: Nomi writes and reads the
multipart envelope itself — the part names, the file names, the boundaries — because those are what
it declared. Each part's *content* is still yours, through its `Stringer` (see
<<multipart-form-data,Multipart form data>>).

== The server

=== `@ServerEndpointService`

Annotate your implementation class:

.ServerArticlesService.kt
[source,kotlin]
----
@ServerEndpointService("articles")
class ServerArticlesService : ArticlesService {
    /* ... */
}
----

The `routeName` argument names the generated `Route` extension — `Route.articles(service:
ServerArticlesService)` here — registering every endpoint of every service the class implements:
exactly the routes the service resolves to (see <<the-service-interface,The service interface>>),
each one decoding its own path and query parameters and answering with the status codes in
<<wire-protocol,Wire protocol>>. You call it once, when mounting the routes (below).

=== Inside an endpoint

[cols="1,2",options="header"]
|===
| Call | Effect

| `Either.error(...)`
| Answers `422` with the serialized business failure.

| `httpError(code, message)`
| Aborts with a standard HTTP status — any code but `422`.

| `routingCall()`
| Reaches the underlying ktor `RoutingCall` for this request.
|===

.ServerArticlesService.kt
[source,kotlin]
----
private fun getArticle(id: Uuid) =
    articles.firstOrNull { (articleId) -> articleId == id }
        ?: httpError(HttpStatusCode.NotFound)
----

`routingCall()` reaches everything ktor itself knows about the request — headers, remote host,
cookies — that isn't already surfaced as a path or query parameter:

.ServerToolsService.kt
[source,kotlin]
----
override suspend fun Tools.Headers.get(): Either<List<Pair<String, List<String>>>, NoFail> {
    val headers = routingCall().request.headers.entries().map { it.key to it.value }.toList()
    return value(headers)
}
----

=== Mounting the routes

.main.kt
[source,kotlin]
----
embeddedServer(
    factory = CIO,
    port = 8080,
) {
    install(ContentNegotiation) {
        json(SharedJson)
    }
    routing {
        articles(ServerArticlesService())
    }
}.start(wait = true)
----

`ContentNegotiation` is not optional — without a converter for the format the client sends, the
server can neither read a request body nor serialize a response.


[[openapi]]
=== OpenAPI

Set `withOpenApiSpecs` and the generated routes describe themselves, so ktor can assemble an OpenAPI
document from the routing tree:

.ServerArticlesService.kt
[source,kotlin]
----
@ServerEndpointService("articles", withOpenApiSpecs = true)
class ServerArticlesService : ArticlesService {
    /** Lists the articles, newest first. */
    override suspend fun Articles.get(page: Int?): Either<List<ArticleSummary>?, NoFail> { ... }
}
----

Nomi describes what it already knows, which is everything a route cannot show by itself: each path
and query parameter with its wire type and whether it is required, the request body — JSON, raw
binary, or a `multipart/form-data` object schema with one property per part — and every status code
the endpoint can answer.
The responses follow <<wire-protocol,the wire protocol>> exactly: `200` with the success schema,
`204` where the success is `Unit` or nullable, `422` with the error schema — *omitted* when the error
type is `NoFail`, since such an endpoint has no business failure — and `400` where a parameter can
fail to decode.

A doc comment on the endpoint becomes its summary and description:

TIP: Write it on the *implementation*, not on the service interface. KDoc does not survive into class
files, so an interface declared in another module — the usual arrangement, since the client shares it
— has none left to read by the time the server processor runs.

Nomi attaches the metadata; serving it is ktor's side. Point Swagger UI at the routing tree:

.main.kt
[source,kotlin]
----
routing {
    swaggerUI("/swagger") {
        source = OpenApiDocSource.Routing()
    }
    articles(ServerArticlesService())
}
----

That needs `io.ktor:ktor-server-swagger` on the server's classpath.

To leave one endpoint out of the document while still serving it, annotate its override:

[source,kotlin]
----
@ServerEndpointService.HideFromOpenApi
override suspend fun Tools.Health.get(): Either<Unit, NoFail> = Either.unit()
----

NOTE: `describe` and `hide` are ktor's own experimental API, so the generated code opts in to
`@ExperimentalKtorApi` — but only for a service that asked for specs. A `Stringer`-encoded path or
query parameter is documented as the string it really is on the wire, without a `format`; and a
streamed `EndpointBinary` is `application/octet-stream`, since its real content type is chosen per
call and there is nothing static to document.

== The client

=== `@ClientEndpointServiceFactory`

Annotate an `object`. It's repeatable, so one object can front several services; `name` becomes
the generated extension function's name:

.APIServices.kt
[source,kotlin]
----
@ClientEndpointServiceFactory(ArticlesService::class, "articles")
object APIServices
----

`APIServices.articles(client)` now returns a `ServiceCaller<ArticlesService>` for any ktor
`HttpClient` you hand it — one function on that object per service it fronts.

[#configuring-the-httpclient]
=== Configuring the `HttpClient`

Nomi does not create or configure the client — the application sets up three things on it:

.main.kt
[source,kotlin]
----
val client = HttpClient {
    install(ContentNegotiation) {
        json(SharedJson)
    }
    defaultRequest {
        url("https://api.example.com/")
        contentType(ContentType.Application.Json)
    }
}
----

- **`ContentNegotiation`, matching the server's format.** Without it a request with a body fails
  while being prepared, and a response body fails to be read.
- **A base URL, in `defaultRequest`, ending in a slash if it carries a path.** This is ordinary URL
  resolution: `https://api.example.com/v1` treats `v1` as a resource to be replaced, silently
  dropping it, whereas `https://api.example.com/v1/` keeps it.
- **A `Content-Type`, in `defaultRequest`.** `ContentNegotiation` picks its converter from the
  request's content type; without one, every `post`, `put` and `patch` fails before reaching the
  network.

Get any of this wrong and a call *throws* rather than returning a `CallStatus` — a misconfigured
client is a programming error, not a call outcome:

[cols="2,2",options="header"]
|===
| Mistake | What is raised

| No `ContentNegotiation`, or no `Content-Type`, on a request with a body
| `IllegalStateException`, from ktor.

| No `ContentNegotiation`, or a format the response doesn't match, when reading a response body
| `NoTransformationFoundException`, from ktor.
|===

=== Calling

.main.kt
[source,kotlin]
----
val result = APIServices.articles(client).call {
    Articles().New().create(ArticleContent(title = "Foo", author = "Me", content = "Bar"))
}
----

The `call { }` block runs with the service as its receiver, so every resource factory and endpoint
method is in scope directly.

It calls exactly one endpoint method.
Building resources is free — only the endpoint call itself counts — but a block calling two of them
fails, so call twice instead.

=== Customizing a request

`call` has a second form for the calls that need it, taking the request customization — headers,
authentication, anything else ktor's `HttpRequestBuilder` exposes — as an extra block, applied to
that one call only:

.main.kt
[source,kotlin]
----
val result = APIServices.tools(client).call({ Tools().Headers().get() }) {
    headers {
        append("X-Nomi-Demo", "Yay!")
    }
}
----

The endpoint call itself moves inside the parentheses here — Kotlin's trailing-lambda syntax always
binds to the *last* parameter, which is the request customization, not the call.

=== Streaming a response

A ktor response is only readable while it is open, and `call` reads the whole body before returning
— so an endpoint whose answer you want to consume as a stream needs a scope to consume it in.
`callStreaming` is that scope: it hands your block a *function* that performs the call, and keeps
the response open for as long as the block runs.

.main.kt
[source,kotlin]
----
articles.callStreaming({ Article(id).get() }) { get ->
    get().mapValue { it.content }
}
----

Whatever the block returns is the call's result, so it can narrow or transform the answer as it
consumes it — the `CallStatus` here carries the mapped `String`, not the whole `ArticleContent`.
The endpoint call moves inside the parentheses for the same reason as above: the trailing lambda
binds to the handler, and a per-call request customization sits between the two when one is needed:

.main.kt
[source,kotlin]
----
articles.callStreaming(
    { Article(id).get() },
    buildRequest = { headers { append("X-Nomi-Demo", "Yay!") } },
) { get ->
    get().mapValue { it.content }
}
----

Failures fold exactly as they do for `call`. A business failure still reaches the handler — `get()`
answers the failing `Either`, and the handler decides what to do with it — while a transport error
or an unexpected status never gets that far and becomes a `NetworkFailure` or a `ServerFailure`
(see <<callstatus,`CallStatus`>>).


==== Streaming a raw response body

An endpoint whose success type is an `EndpointBinary` answers raw bytes: the server writes them
straight to the response channel, with no serialization and no `ContentNegotiation`, exactly as
<<streaming-a-request-body,a streamed request body>> travels the other way.

.ToolsService.kt
[source,kotlin]
----
suspend fun Tools.Download.get(): Either<EndpointBinary, NoFail>
----

.ServerToolsService.kt
[source,kotlin]
----
override suspend fun Tools.Download.get(): Either<EndpointBinary, NoFail> {
    val bytes = "Nomi streams this response.".encodeToByteArray()
    return Either.value(
        EndpointBinary(
            size = bytes.size.toLong(),
            contentType = ContentType.Text.Plain,
            source = { Buffer().apply { write(bytes) } },
        )
    )
}
----

Leave `size` `null` and the response goes out `Transfer-Encoding: chunked`, the honest answer when
the length is not known until the stream ends.

Client-side the binary is read inside the handler, where the response is still open:

.main.kt
[source,kotlin]
----
tools.callStreaming({ Tools().Download().get() }) { get ->
    get().mapValue { binary -> binary.source().use { it.readString() } }
}
----

IMPORTANT: Such an endpoint *must* be called through `callStreaming`. A plain `call` — or a `flow`,
which goes through one — reads and closes the response before returning, leaving nothing to stream,
so Nomi refuses it before the request goes out rather than handing back a binary over a dead
connection.

NOTE: A received response body has the same lifetime rule as a received request body: it is
single-pass, and valid only until the handler returns. Read what you need while you are still
inside it — a binary kept past that point throws on its next read.

=== `CallStatus`

`call { }` returns a `CallStatus.Result`:

[cols="1,3",options="header"]
|===
| Case | Meaning

| `Success(value)`
| The endpoint answered `200`/`204`.

| `CallFailure(error)`
| The endpoint answered `422` with a business failure.

| `ServerFailure(code, body)`
| The server answered any other non-success status.

| `NetworkFailure(message, cause)`
| The request never reached the server.
|===

`CallStatus` additionally carries a `Loading` state, so the same type also models a call still in
flight in a UI. Two kinds of throwable are deliberately *not* folded into a result: a
`CancellationException` raised mid-call propagates unchanged (so cancelling the caller's scope
still cancels it), and so do the client-misconfiguration exceptions above (retrying or handling
them as a `NetworkFailure` would never fix what's actually wrong).

[cols="1,3",options="header"]
|===
| Function | Behaviour

| `successOrNull()`
| The success value, or `null` for anything else.

| `mapSuccess { }` / `mapFailure { }`
| Transforms the success/failure payload, passing every other case through unchanged.

| `fakeSuccess()` / `fakeFailure()` / `fake()`
| Widens a `CallStatus` known never to hold one side (typically after a `NoFail` check) to a
  broader type — a variance escape hatch, not a runtime check.
|===

=== Flows

A call also comes as a cold `Flow<CallStatus<S, F>>`, for the UI that wants the `Loading` state as
an emission rather than as a separate piece of bookkeeping. Three builders produce one:

[cols="1,3",options="header"]
|===
| Builder | Emits

| `caller.flow { }`
| `Loading`, then one endpoint call's result.

| `callFlow { }`
| `Loading`, then the result of any `suspend` function returning a `CallStatus.Result`.

| `callChainFlow { }`
| `Loading`, then the single result of a whole <<chains,chain>> of calls.
|===

`flow { }` is ``call { }``'s `Flow` form, and takes the same optional request customization as a
second block:

.main.kt
[source,kotlin]
----
APIServices.articles(client)
    .flow { Articles().get(page = 1) }
    .collect { status ->
        when (status) {
            CallStatus.Loading -> println("Loading…")
            is CallStatus.Success -> println(status.success)
            is CallStatus.Failure -> println("Failed: $status")
        }
    }
----

The three branches above are exhaustive: `Loading` is the only state that is neither a `Success`
nor a `Failure`.

Every one of these flows is *cold*. Nothing is called until the flow is collected, and each
collection calls again — so a retry is simply another collection.

`callFlow { }` is the same wrapper over anything that answers a `CallStatus.Result`, not just a
single endpoint call — a repository function that already folds several calls together, say:

.ArticleRepository.kt
[source,kotlin]
----
class ArticleRepository(private val articles: ServiceCaller<ArticlesService>) {

    suspend fun page(page: Int): CallStatus.Result<List<ArticleSummary>?, NoFail> =
        articles.call { Articles().get(page = page) }

    fun pageFlow(page: Int): Flow<CallStatus<List<ArticleSummary>?, NoFail>> =
        callFlow { page(page) }
}
----

Two operators read the states as they go by, leaving the flow untouched: `onSuccess { }` runs on
every `Success`, `onFailure { }` on every `Failure`.

=== Chains

`callChainFlow { }` runs several calls as one unit: the whole chain emits one `Loading` and then a
single `CallStatus.Result`, whichever call it ends up coming from.

Inside the block, `link { }` starts a call and hands back its success value as a `Deferred`:

.main.kt
[source,kotlin]
----
sealed interface FailedCAAPC : Error {
    data class FailedArticleCreation(val error: ArticleCreationFailure) : FailedCAAPC
    data class FailedCommentPost(val error: ArticleCommentPostFailure) : FailedCAAPC
}

suspend fun createArticleAndPostComment(
    articles: ServiceCaller<ArticlesService>,
): Flow<CallStatus<Unit, FailedCAAPC>> =
    callChainFlow {
        val id = link {
            articles
                .call { Articles().New().create(ArticleContent(title = "Foo", author = "Me", content = "Bar")) }
                .mapFailure { FailedCAAPC.FailedArticleCreation(it) }
        }

        articles
            .call { Article(id.await()).Comments().post(ArticleComment(author = "Me", content = "Hello World!")) }
            .mapFailure { FailedCAAPC.FailedCommentPost(it) }
    }
----

Every call in a chain reports the same failure type, so each one's own `E` is mapped into it with
`mapFailure { }` — which is what makes the chain's result a single type a caller can act on.

The block's own return value is the chain's result when every link succeeded. Otherwise the *first
link to fail* is the result, with its failure reported as-is:

- A failed link's `Deferred` never completes, so an `await()` on it never resumes. The chain is
  cancelled around it instead, which is why the block after that point does not run.
- That cancellation stays inside the chain. The collector's scope is untouched: a failed chain
  emits a `Failure` rather than cancelling its caller.
- The links are cancelled too, so a chain never leaves a call in flight behind it.

Links run in the chain's own scope, so every link started before the first `await()` runs
*concurrently* — a chain is only sequential where you make it sequential by awaiting:

[source,kotlin]
----
callChainFlow {
    val summaries = link { articles.call { Articles().get(page = 1) } }   // <1>
    val content = link { articles.call { Article(knownId).get() } }       // <1>
    CallStatus.Success(summaries.await() to content.await())              // <2>
}
----
<1> Both calls are already in flight here.
<2> Awaited only once both are needed — either failing ends the chain.

`callChain { }` is the same builder without the `Flow`, returning the `CallStatus.Result` directly,
and `linkChain { }` nests a whole chain inside one link of an outer chain.

NOTE: `callChainFlow` is itself a `suspend` function, so it is called from a coroutine even though,
being cold, it runs nothing until collected. `callFlow` and `flow` are not.

== Supported platforms

`nomi-runtime-shared` and `nomi-runtime-client` are Kotlin Multiplatform libraries targeting:

* *JVM*
* *iOS* — `iosArm64`, `iosSimulatorArm64`, `iosX64`
* *watchOS* — `watchosArm32`, `watchosArm64`, `watchosDeviceArm64`, `watchosSimulatorArm64`
* *tvOS* — `tvosArm64`, `tvosSimulatorArm64`
* *macOS* — `macosArm64`
* *Android Native* — `androidNativeArm32`, `androidNativeArm64`, `androidNativeX64`, `androidNativeX86`
* *Linux* — `linuxX64`, `linuxArm64`
* *Windows* — `mingwX64`
* *JS* — browser, Node.js
* *Wasm/JS* — browser, Node.js

`macosX64` (Intel macOS) is deliberately not a target: Kotlin deprecated it in 2.3.20 and will
remove it. `iosX64` — the Intel iOS _simulator_, not Intel hardware — is kept because it is still a
supported target.

`nomi-runtime-server` is JVM-only, built on ktor-server.

== Visibility

Every declaration Nomi reads — resource, service, `Stringer` object, `@Endpoint.MultipartFormData`
part type, `@ServerEndpointService` class, `@ClientEndpointServiceFactory` object — may be `public`
or `internal`. Whichever it is, the
code the processors generate from it carries the same visibility: an `internal` service gets an
`internal Route` extension, named after its `routeName`, an `internal` resource gets an `internal`
factory, and so on.
